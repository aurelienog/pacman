# Technical Challenges & Lessons Learned

Throughout the development of the project, several technical challenges emerged while implementing the game engine, designing the asset pipeline, and integrating the rendering system. Although none of these issues blocked the project completely, they required architectural decisions and multiple design iterations before reaching a stable solution.

## Technical Challenges

| Area                                     | Challenge                                                                                                                                                                                                                                                  | Resolution                                                                                                                                                                                                                                                                                                                     | Outcome                                                                                                                                          |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Rendering & Gameplay Synchronization** | Grid-based simulation and interpolated rendering could make collisions appear visually too early or too late. | Kept collisions discrete while using movement progress to delay logical cell occupation until it better matches the rendered position. | More consistent collision feedback without coupling gameplay to rendering. |
| **Gameplay Fairness**                    | Immediate cell transitions could make collisions feel unfair from the player's perspective.                                                                                      | The collision system now favours the player's visual perception by delaying tile occupation until the entity has progressed sufficiently into the destination cell, while frightened ghost collisions remain strictly cell-based to ensure responsive gameplay.                                                                | The resulting gameplay feels more intuitive without increasing the complexity of the AI or collision algorithms.                                 |
| **Ghost AI & Pathfinding** | The initial ghost movement relied only on Manhattan distance to select the next move. Although simple, this approach frequently produced unintelligent behaviour, with ghosts getting trapped, taking poor routes and failing to resemble the behaviour of the original Pac-Man ghosts. | The movement system was redesigned using **Breadth-First Search (BFS)** to compute shortest paths on the maze. On top of this, each ghost was given its own targeting strategy (Blinky, Pinky, Inky and Clyde), while additional behaviours were implemented for **Frightened** and **Respawning** states. | Ghost movement became significantly more believable and challenging, providing a gameplay experience much closer to the original Pac-Man while keeping the AI modular and easy to extend. |
| **MLX Graphical Primitives Compliance**  | High-level Pygame features (e.g., `Rect.collidepoint`, multi-layer alpha glow surfaces, custom vector shapes) violated strict evaluation rules requiring every graphical call to have a direct equivalent in the MLX library.                               | Replaced high-level Pygame helpers with pure mathematical boundary checks (`left <= x <= right`), eliminated multi-layer alpha surfaces, and converted visual elements into pre-rendered static PNG assets and sprite blitting routines.                                                                                     | Achieved 100% compliance with strict 42 School graphical library constraints while retaining a high-quality sci-fi aesthetic.                 |
| **Responsive UI & Dynamic Resolution**   | Fixed pixel coordinates and static font sizes caused HUD elements, instruction cards, and menu frames to distort or overlap when window dimensions were stretched or resized.                                                                               | Re-engineered all UI drawing routines to calculate positions, font sizes, column widths, and line thicknesses dynamically as proportional fractions of the current screen dimensions (`screen.get_width()` / `screen.get_height()`).                                                                                   | UI components scale fluidly across arbitrary window sizes (from 800x600 to 1080p and beyond) without layout overlap or text truncation.         |
| **Sprite Atlas & Animation Slicing**     | Multi-frame sprite atlases required directional animation, skirt walking toggles, and state switching without relying on runtime image flipping or rotation methods forbidden in basic MLX.                                                                | Split ghost atlases into modular color components (`red`, `pink`, `cyan`, `orange`), created a dedicated `utils_sprite_atlas` for items/states, pre-rendered directional frames natively, and added vertical offset controls (`GHOST_Y_OFFSET`).                                                                       | Produced smooth chewing animations, directional ghost eye movement, and static corner-matched Super Pacgums without runtime image transformations. |


## Lessons Learned

Several important lessons were learned throughout the development of the project:

* **Architecture first:** Defining clear boundaries between the **Domain**, **Game Logic** and **Rendering** layers early reduced coupling and made parallel development and later refactoring easier.
* **Interfaces matter:** Defining stable interfaces between the simulation and rendering layers allowed both developers to work independently while keeping integration manageable.
* **Start simple, then improve:** The initial Manhattan-distance ghost movement provided a working baseline, while evolving it into **BFS pathfinding with individual ghost personalities** significantly improved gameplay quality.
* **Gameplay perception matters:** The collision system showed that technically correct behaviour is not always sufficient; gameplay timing must also match what the player sees.
* **Design for constraints:** Using simple graphical primitives and modular asset loaders from the beginning reduced the impact of the strict MLX compatibility requirements.
* **Parallel development accelerates delivery:** Developing the rendering system alongside the core engine allowed a functional prototype to emerge earlier and helped identify integration issues sooner.
* **Automated quality checks:** Continuous use of **flake8** and **mypy**, together with unit and integration testing, made refactoring safer and reduced the risk of accumulating technical debt.
* **Communication reduces integration risk:** Frequent peer reviews and coordination between developers helped maintain consistent architectural decisions while different components evolved in parallel.
